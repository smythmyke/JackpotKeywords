## 1. What x402 is (1-paragraph recap)

x402 is an open payment protocol (originated by Coinbase, May 2025) that revives the dormant **HTTP `402 Payment Required`** status code so a client can pay for a request **inline, machine-to-machine**, with no account, API key, or human checkout. The server answers an unpaid request with `402` + a JSON body describing payment requirements (scheme, price, asset, recipient, network). The client constructs a signed stablecoin payment (USDC on Base) and **retries the same request** with an `X-PAYMENT` header. A **facilitator** (Stripe's, in our case) verifies/settles on-chain and the server returns the resource plus an `X-PAYMENT-RESPONSE` confirmation. Full background: the two research summaries linked in §0.

**Why JK cares:** autonomous agents (the audience the MCP server already targets) can't click a Stripe checkout page or provision a `jk_live_` key out-of-band. x402 lets an agent discover-and-pay in one HTTP round-trip. It's a bet on agent-to-agent demand, not a replacement for the prepaid-key model.

## 2. Goals / non-goals

**Goals**
- Add **one** x402-gated, pay-per-call path behind a feature flag, settling real USDC into the existing Stripe account.
- **Zero JSON-RPC schema change** — an MCP tool can surface the 402 without altering its tool contract.
- **Reuse the existing pipeline verbatim** (`runRecommendPipeline`) — only auth/settlement differs.
- Keep the prepaid `jk_live_` + `balanceCents` model fully intact and untouched on its own routes.
- Produce a **portable runbook** so the other three servers can clone it (mirrors `RAPIDAPI-REPLICATION-RUNBOOK.md`).

**Non-goals (v1)**
- Not replacing the prepaid-credit model. x402 is additive.
- Not converting all four billable endpoints — one route only.
- Not building our own facilitator or touching a chain directly — Stripe is the facilitator.
- Not supporting non-Base networks (Solana/Tempo) at launch even though Stripe lists them.

## 3. The HTTP 402 collision (must-read for future devs)

JK **already returns HTTP 402** — `insufficient_balance` on the keyed prepaid routes (`v1.ts:264, 408, 513, 611, 735`). That is a *"you ran out of prepaid credit, go top up"* signal aimed at a **human/keyed** caller. x402 also uses 402, but as a *"here is how to pay right now, machine-to-machine"* challenge. **These are different semantics on different routes/sources** and must not be conflated:

| | Prepaid 402 (existing) | x402 challenge (new) |
|---|---|---|
| Route | `/v1/recommend` etc. with `Bearer jk_live_` | x402-gated route/source (§4) |
| Body | `{ error: "insufficient_balance", ... }` | x402 payment-requirements JSON (`accepts`, `payTo`, `price`, `network`) |
| Caller | keyed customer with a prepaid balance | anonymous agent paying inline |
| Resolution | call `POST /v1/topup` (human card checkout) | send USDC, retry with `X-PAYMENT` |

Keep them on **distinct sources** so dashboards, logs, and the `recordApiCallResult` ledger never mix them.

## 4. Integration model — decision

Two ways to wire x402 in. **Recommended: Model A** (matches the roadmap's "pay-per-call without a human checkout" intent).

### Model A — pure pay-per-call gate (RECOMMENDED)
A request with no payment → `402` + x402 challenge → agent pays USDC → retries with `X-PAYMENT` → we verify, run the pipeline, settle. **No prepaid balance, no signup, no key.** This is the true machine-native flow and the only one that delivers "no human checkout."

- **How callers reach it:** add an x402 path *alongside* the keyed one, not replacing it. Either (a) a dedicated route `POST /v1/x402/recommend`, or (b) the existing `POST /v1/recommend` branches to the x402 flow **only when no `Bearer` key is present AND `JK_X402_ENABLED=1`**. **Recommend (a)** for the spike — a separate route keeps the existing handler untouched and is trivially flag-gated/removable.
- **Billing:** does **not** call `deductBalance`. Settlement *is* the payment. Logged to `apiCalls` with `source: 'x402'`, `costCents`, and a settlement reference (PaymentIntent id + on-chain tx hash).

### Model B — x402 as a top-up rail (fallback)
Keep `jk_live_` + `balanceCents`; let agents fund their balance via USDC instead of card checkout (an x402 variant of `POST /v1/topup`). Reuses 100% of billing, but **still requires a key + a funding step**, so it does *not* satisfy "no human checkout." Keep as a fallback if Model A's per-call settlement proves too heavy or Stripe's per-tx fee makes $0.10 calls uneconomic (§9-D2).

## 5. Pilot route & price

Pilot on **`recommend-deep` ($0.30)**, not `recommend` ($0.10). Rationale:
- The roadmap *intended* the $0.30 tool (the "$0.30 metered" phrasing); recommend-deep is it.
- A higher unit price gives more headroom against an unknown Stripe per-tx crypto fee — a fixed fee that's tolerable on 30¢ could erase the margin on 10¢ (§9-D2).
- recommend-deep returns the richest payload (clusters + categories + competitors), so it's the most compelling "an agent paid for this and got real value" demo.

Open to piloting `recommend` at $0.10 instead if fees turn out negligible — decision **D1** in §9.

## 6. Detailed design (Model A)

### 6.1 Request flow
```
Agent ──GET/POST (no payment)──▶ /v1/x402/recommend
                                  │  flag on? yes
                                  │  create Stripe PaymentIntent (crypto/deposit/base, amount=price)
                                  ▼
Agent ◀──402 + x402 challenge──── { accepts:[{scheme:"exact", price:"$0.30",
                                    network:"eip155:8453", payTo:<deposit addr>}], ... }
   │ agent's wallet sends USDC to payTo, builds X-PAYMENT
   ▼
Agent ──POST + X-PAYMENT────────▶ /v1/x402/recommend
                                  │  1. VERIFY payment via Stripe facilitator (settled/au­thorized?)
                                  │  2. idempotency: this PaymentIntent not already fulfilled?
                                  │  3. run runRecommendPipeline({...}, {deep:true})
                                  │  4a. success → log apiCall(source:'x402', settled) ; return result
                                  │  4b. failure → refund the PaymentIntent ; log failure
                                  ▼
Agent ◀──200 + X-PAYMENT-RESPONSE result JSON
```

### 6.2 Settlement primitive (Stripe)
Per Stripe's x402 docs, the server mints a `PaymentIntent` that yields a Base deposit address:
```ts
const pi = await stripe.paymentIntents.create({
  amount: RECOMMEND_DEEP_COST_CENTS,   // 30
  currency: 'usd',
  payment_method_types: ['crypto'],
  payment_method_options: { crypto: { mode: 'deposit', deposit_options: { networks: ['base'] } } },
  confirm: true,
}, { /* preview API version */ });
const payTo = pi.next_action.crypto_display_details.deposit_addresses['base'].address;
```
Stripe **auto-captures** the PaymentIntent when the USDC deposit confirms on-chain. Sandbox doesn't watch testnets — use Stripe's `simulate_crypto_deposit` test helper + the **`purl`** CLI (Stripe's open-source x402 test client) to exercise the flow locally.

> ⚠️ **Funds-first caveat.** Stripe's deposit model means money arrives *before* we run the pipeline, so we cannot use the cleaner x402 "verify-then-settle-on-success" pattern (where a facilitator validates a signed authorization but only broadcasts on success). Our failure path must therefore **refund the PaymentIntent** — the on-chain analog of the existing `refundBalance` deduct-then-refund contract. Confirm Stripe supports refunding a crypto-deposit PaymentIntent back to the payer wallet (**D3**); if not, fall back to issuing the payer a one-call retry credit keyed by their wallet address.

### 6.4 ESM/CJS resolution
Stripe's `@x402/*` middleware is ESM + Hono. JK is CJS + Express. In priority order:
1. **Hand-roll the 402 against Express** (recommended for the spike). The protocol is a 402 body + an `X-PAYMENT` header parse + a Stripe verify call — small, and it keeps us off Hono entirely. We already hand-roll comparable middleware (the RapidAPI billing-header patch, `v1.ts:77-88`).
2. If a `@x402/express` adapter exists/ships, use it via **dynamic `import()`** from the CJS function (same technique scoped for the OpenAI SDK in SURF-3).
3. Last resort: mount a tiny Hono sub-app — rejected; adds a framework for one route.

### 6.5 Security & correctness
- **Verify server-side before running.** Never run the pipeline on an unverified `X-PAYMENT` — confirm the PaymentIntent is captured/authorized for the right amount via Stripe before doing any work.
- **Idempotency / replay.** Key fulfillment on the PaymentIntent id; refuse to run twice for the same payment (an agent retrying the request must not re-trigger a paid pipeline run). Store a short-lived `x402Fulfillments/{paymentIntentId}` marker.
- **Amount/asset check.** Reject if paid amount < price, wrong asset, or wrong network.
- **Rate limiting.** The keyed limiter is per-customer; x402 has no customer. Add an IP/wallet-keyed limiter on the x402 route to bound abuse of the (cheap but non-zero) PaymentIntent-creation step.
- **Flag-off = 404/disabled**, never a silent fall-through to a keyed path.

### 6.6 Attribution
`source:'x402'` flows into the existing `apiCalls` ledger, so the seller dashboard's source rollups pick it up once `ApiSource` is widened (this also satisfies part of the deferred SURF-ATTR-1). Distinct `jackpotkeywords-x402/…` UA on any first-party caller for forward-compatible granular attribution.

## 8. Prereqs & risks

**Prereqs**
- Stripe dashboard approval for "Stablecoins and Crypto" (review + possible contact — lead time unknown).
- Pin/verify Stripe preview API version `2026-03-04.preview` against the live SDK.
- `purl` CLI installed for testing.

**Risks**
- **Preview instability.** Preview API + preview product = breaking changes possible. Keep all Stripe-preview surface in `services/x402.ts`.
- **Fee economics (the kill-switch risk).** If Stripe's per-tx crypto fee has a fixed floor, micro-priced calls may be margin-negative. **Confirm before 1b** (§9-D2).
- **Demand risk.** Agent-to-agent payment may simply not show up yet. That's *the bet* — bounded by the flag; parked code costs nothing.
- **Refundability of crypto deposits** (§9-D3) — if Stripe can't refund to the payer wallet, the failure UX degrades to a retry credit.
- **No human in the loop on disputes.** Unlike card payments, an on-chain USDC settlement has no chargeback path; correctness of the verify step is load-bearing.

## 11. MPP vs x402 — decision (added 2026-06-02)

**Question that prompted this:** card-paying agents are a larger audience than USDC-wallet agents today, so why lead with x402/crypto instead of Stripe's card-capable **Machine Payments Protocol (MPP)**? Research below; **conclusion: keep x402 as the spike, adopt MPP as the X402-1c expansion — not a teardown.**

### 11.1 What MPP is
MPP is Stripe's broader machine-payments protocol ([docs](https://docs.stripe.com/payments/machine/mpp), launched **2026-03-18**). Like x402 it's an **HTTP-402** challenge/credential/receipt flow, but it advertises **multiple payment methods in one 402 response**: crypto (Tempo/Solana) **and** fiat cards/Link via **Shared Payment Tokens (SPTs)**. Same preview API version as x402 (`2026-03-04.preview`). Integrated via the `mppx` SDK (`Mppx.compose(...)` — TS/Python/Rust, **ESM**).

### 11.2 Why card-via-MPP is *not* a clean "lead with card"
| Factor | Reality (verified 2026-06-02) |
|---|---|
| "Any card"? | **No.** SPT fiat needs the agent to hold a **Stripe Link Shared Payment Token** (`@stripe/link-cli`), and **both client + server need a Stripe account**. Reach > crypto-wallet agents, but < "everyone with a Visa." |
| Minimum charge | **SPT fiat min = $0.50.** JK `recommend-deep` is $0.30 → below the floor. Must reprice ≥$0.50, bundle, or use the deposit/session model. |
| Maturity | MPP is ~11 weeks old (vs x402's longer track record, ~131k tx/day early Mar 2026, ~half testing). Both preview. |
| Implementation lift | **More than x402**, not less: `mppx` SDK (ESM/CJS friction), a Stripe "profile" (`networkId profile_…`), SPT-credential validation. |
| Crypto network | Stripe **x402 = Base** (where the open x402 ecosystem lives); Stripe **MPP crypto = Tempo/Solana**. Not a drop-in for our Base spike. |
| Fees | MPP card pricing **undisclosed** (contact sales); the deposit/voucher model claims "near-zero per-request" via batch settlement. Crypto rail = flat **1.5%** (confirmed §0). |

### 11.3 The reframe — JK already serves card-paying agents
"Deposit upfront, draw down per call, batch-settle" (MPP's own economic model) **is the existing `jk_live_` + `/v1/topup` prepaid flow** (top up once by card, spend $0.30/call, no per-call card fee). MPP-SPT's *only genuinely new* card capability is **zero-onboarding inline first-touch** (no pre-provisioned key) — valuable, but bounded by the Link-SPT requirement and the $0.50 floor. So "lead with card" is largely "the product already shipped," plus a slicker onboarding wrapper.

### 11.4 The useful end-state ("why not both")
`mppx`'s `Mppx.compose` returns **one 402 challenge offering both a crypto option and a card option** — the agent picks. The mature architecture is therefore a **single 402 endpoint, card + crypto**, which would eventually **supersede the hand-rolled `services/x402.ts`**. Independent guidance agrees with the sequencing: WorkOS — *"start with x402 for low-commitment adoption; layer MPP as needs evolve."*

### 11.5 Decision
- **Keep X402-1a as-is** (Base, built, tsc-clean, parked behind the flag at $0). It's the right low-commitment spike and reaches the open Base ecosystem.
- **Promote MPP to the X402-1c expansion** (rename the track "Machine Payments — x402 + MPP"), adopted via `mppx` for card+crypto in one endpoint. **Gate adoption on:** (a) MPP reaching GA; (b) confirmed SPT pricing + a sub-$0.50 workaround (reprice/bundle/session-balance); (c) a Base-vs-Tempo crypto-network decision.
- The card-audience point is real — pursued as the **evolution**, not by tearing up the spike.
